# Brute-Force-JWT-Signing-Secret

## Summary

This procedure demonstrates how to brute-force the secret key used for signing a JSON Web Token (JWT) with the HS256 algorithm (HMAC-SHA256). By cracking the secret, an attacker can forge valid JWTs to impersonate users, access restricted resources, or escalate privileges in web applications relying on JWT for authentication.

## Description

JWTs are self-contained tokens used for secure information exchange, consisting of a header, payload, and signature separated by dots (e.g., header.payload.signature). For symmetric signing algorithms like HS256, the signature is generated by HMAC-SHA256 of the base64url-encoded header and payload (the 'message') using a secret key. If the secret is weak (short, dictionary-based, or predictable), it can be brute-forced offline by treating the signature as a hash and the message as a salt in a cracking tool like Hashcat. This procedure assumes the attacker has captured a valid JWT from network traffic or a client-side source and is performing offline cracking. Success enables token forgery for unauthorized access. This is effective against misconfigurations where secrets are not sufficiently random or long (e.g., < 32 characters).

## Requirements

1. A captured valid JWT token using HS256 (verify via jwt.io or similar).
2. Hashcat installed on a system with GPU acceleration for faster cracking.
3. A wordlist or mask for brute-forcing (e.g., rockyou.txt for dictionary attacks or ?a?a?a... for pure brute force).
4. Basic command-line knowledge and access to a Linux environment.
5. The JWT must use a symmetric algorithm (alg: HS256); asymmetric (RS256) requires different approaches like private key theft.

## Defense

- Use strong, randomly generated secrets (at least 256 bits of entropy, e.g., via cryptographically secure random generators).
- Implement key rotation and store secrets securely (e.g., in HSMs or environment variables, not in code).
- Enforce algorithm restrictions (reject HS* algorithms if possible, prefer RS256 with public key validation).
- Monitor for anomalous token usage, such as high failure rates or unexpected token origins.
- Rate-limit token validation and log all validation attempts for anomaly detection.

## Objectives

1. Extract the message (base64(header).base64(payload)) and signature from the captured JWT.
2. Format the data for offline cracking using Hashcat to recover the signing secret.
3. Verify the cracked secret by forging a new JWT and testing it against the target application.
4. Use the secret to generate arbitrary tokens for impersonation or privilege escalation.

## Instructions

### Step 1: Decode and Extract JWT Components

**Context**: Parse the JWT to isolate the message (concatenated base64url-encoded header and payload) and the signature. This prepares the data for Hashcat, where the message acts as the salt and the signature as the target hash. Use base64url decoding to ensure correct formatting without padding issues.

**Command** ([[commands/jwt-extract-message-and-signature]]):
```bash
python3 -c "import sys, base64, jwt; token = sys.argv[1]; header, payload, sig = token.split('.'); msg = f'{header}.{payload}'; print(f'Message: {msg}'); sig_hex = base64.urlsafe_b64decode(sig + '==').hex(); print(f'Signature Hex: {sig_hex}');" $_JWT_TOKEN
```

> This Python one-liner (using the PyJWT library if installed, or pure base64) decodes the token and outputs the message and hex-encoded signature. Save the outputs to files: message.txt and signature.hex. Expected output includes the raw message string and a 64-character hex signature. If PyJWT is unavailable, use online tools like jwt.io for initial decoding, but avoid for sensitive tokens.

### Step 2: Prepare Hash File for Cracking

**Context**: Hashcat requires a specific format for HMAC-SHA256 cracking: salt:hash (message:signature_hex). Create a hash file with this format to enable dictionary or brute-force attacks on the secret.

**Command** (Custom preparation):
```bash
echo "$(cat message.txt):$(cat signature.hex)" > jwt_hash.txt
```

> This combines the message and signature into Hashcat's expected input format. Verify the file contents match: a single line with message:sig_hex. This step ensures the cracking targets the correct HMAC computation.

### Step 3: Brute-Force the Secret with Hashcat

**Context**: Run Hashcat in dictionary or brute-force mode to recover the secret. Mode 1450 handles HMAC-SHA256 where the key (secret) is cracked against the known salt (message) and hash (signature). Start with a dictionary attack; escalate to masks if needed. Use GPU for performance; cracking time depends on secret strength (e.g., 8-char alphanumeric: hours; 32-char random: infeasible).

**Command** ([[commands/hashcat-crack-hmac-sha256]]):
```bash
hashcat -m 1450 -a 0 $_WORDLIST jwt_hash.txt --potfile-disable
```

> Replace $_WORDLIST with a path like /usr/share/wordlists/rockyou.txt. The -m 1450 specifies HMAC-SHA256, -a 0 for dictionary attack. Expected output: If successful, Hashcat displays the cracked secret (e.g., 'Secret found: weaksecret123'). Check potfile or console for results. For brute force, use -a 3 with a mask like -a 3 jwt_hash.txt ?a?a?a?a?a?a?a?a. If no match, increase complexity or use rules (-r rules/best64.rule).

### Step 4: Verify and Forge Token with Cracked Secret

**Context**: Test the recovered secret by generating a new JWT with modified claims (e.g., admin privileges) and validating it against the target endpoint. This confirms the crack and demonstrates impact.

**Command** (Using jwt tool or Python):
```bash
python3 -c "import jwt; encoded = jwt.encode({'user': 'attacker', 'admin': True}, '$_CRACKED_SECRET', algorithm='HS256'); print(encoded)"
```

> Substitute $_CRACKED_SECRET with the found key. Expected output: A new JWT string. Submit it to the application's auth endpoint (e.g., via curl). Success: Access granted without errors, confirming impersonation capability.
