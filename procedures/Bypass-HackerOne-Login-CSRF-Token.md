# Bypass-HackerOne-Login-CSRF-Token

## Summary

This procedure exploits a CSRF token bypass vulnerability in the HackerOne login process (Ruby on Rails with Devise) by capturing and modifying login requests to omit the authenticity_token, allowing attackers to force victim authentication without proper verification, leading to session takeover or data manipulation.

## Description

The vulnerability occurs because the server includes an authenticity_token in the login form but fails to enforce its presence or validity during POST to /users/sign_in. Attackers use Burp Suite to intercept a legitimate login, generate a CSRF PoC HTML form, remove the token, and host it to trick victims into submitting their credentials. This logs the victim into the site (potentially under attacker control for IP logging or adding payment info), enabling identity theft or brute force preparation. Target environment is web-based, requiring no special access beyond internet connectivity. Expected outcomes include successful unauthorized login and session establishment.

## Requirements

1. Burp Suite installed and configured as a browser proxy for request interception
2. Access to a test account on HackerOne for initial capture (or simulated credentials)
3. Ability to host malicious HTML (e.g., attacker server) for victim delivery via phishing
4. Victim's email and password (social engineered or guessed)

## Defense

Defensive measures and detection strategies:

- Implement strict CSRF token validation on all state-changing endpoints, rejecting requests without valid tokens
- Use SameSite=Strict cookies to prevent cross-site submission
- Monitor for anomalous login patterns, such as logins from unfamiliar IPs or user agents
- Enable rate limiting on login attempts and log all authentication events for anomaly detection

## Objectives

1. Bypass CSRF protection to submit login requests without tokens
2. Force victim authentication to capture session or add sensitive data
3. Validate the bypass by confirming successful login and non-authenticated sessions post-fix

## Instructions

### Step 1: Capture and Analyze Login Request

**Context**: Intercept a standard login to identify the token field for later removal.

**Command** ([[commands/hackerone-csrf-poc-submit]]): Use Burp Suite to proxy and capture.

No direct command; configure Burp proxy and submit form manually.

> Expected: POST request with user[email], user[password], user[remember_me], authenticity_token visible.

### Step 2: Generate and Modify CSRF PoC

**Context**: Create and edit the PoC to remove token dependency.

**Command** ([[commands/hackerone-csrf-poc-submit]]):

```html
<html><!--CSRF PoC - generated by Burp Suite Professional --><body><script>history.pushState('','','/')</script><form action="https://hackerone.com/users/sign_in" method="POST"><input type="hidden" name="user[email]" value="victim@example.com"/><input type="hidden" name="user[password]" value="victimpass123"/><input type="hidden" name="user[remember_me]" value="1"/><input type="submit" value="Submit request"/></form></body></html>
```

> Explanation: Generate via Burp Engagement Tools, then manually remove authenticity_token input. Host and lure victim to load. Expected: Form submits without token.

### Step 3: Submit Modified Request and Verify

**Context**: Test the bypass and check session status.

**Command** ([[commands/hackerone-session-check]]):

```http
GET /current_user.json HTTP/1.1
Cookie: session=extracted_session_id;
```

> After submission, verify login success. For retest, use [[commands/hackerone-invalid-token-test]] to ensure fix rejects arrays. Expected: Successful redirect if vulnerable; 400 if fixed.
