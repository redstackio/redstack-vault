# Intercept-and-Redirect-iFrame-via-Proxy

## Summary

This procedure uses a proxy to intercept the iFrame load request generated by Invision Community's embedding feature and redirects it to the malicious reflected XSS URL, injecting the payload into stored content.

## Description

When the forum software processes the embedded link, it fetches content for the iFrame, which the attacker intercepts via proxy (e.g., MITM setup). The redirect tricks the server into embedding the XSS payload instead of benign content. Target: Server-side iFrame requests during post save. Prerequisites: Embedded link from prior step, proxy configured for interception. Outcomes: Payload stored as if it were legitimate embed content.

## Requirements

1. Running proxy tool capable of request interception and modification
2. Network position to proxy traffic (local or remote setup)
3. Malicious URL ready for redirection

## Defense

Defensive measures and detection strategies:

- Validate iFrame sources with whitelists or CSP
- Monitor for proxy-like redirects in embed fetches
- Rate-limit or log external embed requests

## Objectives

1. Capture the iFrame load from forum server
2. Redirect to RXSS URL for payload injection
3. Ensure storage without validation failures

## Instructions

### Step 1: Configure Proxy

**Context**: Set up the proxy to intercept forum traffic.

Launch the proxy and configure the browser or system to route traffic through it, focusing on the forum domain.

### Step 2: Trigger Embed Request

**Context**: Save the post/profile to initiate iFrame load.

Submit the content containing the link; monitor proxy for the outgoing request to the embedded URL.

### Step 3: Intercept and Redirect

**Context**: Modify the request to point to the malicious URL.

In the proxy interface, capture the iFrame GET request and edit the destination to the crafted RXSS URL, then forward.

> This causes the server to fetch and embed the XSS content, storing it persistently.
