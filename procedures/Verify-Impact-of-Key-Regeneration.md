# Verify-Impact-of-Key-Regeneration

## Summary

This procedure tests the success of the CSRF attack by attempting account access with the old and new personal keys, confirming the unauthorized regeneration and potential lockout.

## Description

Post-attack, the victim's old personal key is invalidated server-side upon regeneration. Logging out and retrying login with the old key fails, while the new key (displayed after redirect) succeeds. This verifies the denial-of-service impact, especially in recovery scenarios like lost devices.

## Requirements

1. Access to the victim's account credentials (username/password)
2. The new personal key from the post-attack redirect
3. Browser to perform login tests

## Defense

Defensive measures and detection strategies:

- Require confirmation prompts for key regenerations
- Audit logs for unexpected key changes and notify users
- Rate-limit key generation attempts

## Objectives

1. Demonstrate old key invalidation
2. Confirm new key functionality
3. Highlight account access denial risks

## Instructions

### Step 1: Log Out and Test Old Key

**Context**: Verify the key change by attempting login with the pre-attack key.

Log out of staging.login.gov, then log back in using username/password and the old personal key.

**Expected Output**: Login fails with error indicating invalid personal key.

### Step 2: Test New Key Access

**Context**: Use the key generated by the attack to confirm successful takeover effect.

Repeat login but enter the new personal key shown after the CSRF redirect.

**Expected Output**: Successful login, proving the key was regenerated without consent.
