# MySQL-Error-Based-SQL-Injection-with-Select-for-Version-Extraction

## Summary

This procedure demonstrates an error-based SQL injection attack targeting MySQL databases (version 4.1 or higher) using a crafted SELECT statement. By injecting a payload that triggers a duplicate entry error, the attacker can force the database to leak sensitive information, such as the server version, through the error message returned by the application.

## Description

Error-based SQL injection exploits applications that do not properly sanitize user inputs in SQL queries, allowing attackers to inject malicious SQL code. In MySQL, this technique leverages error messages generated by operations like GROUP BY with RAND() to extract data. The payload uses a subquery with COUNT(*), CONCAT to append the version (via @@VERSION), and FLOOR(RAND()*2) to create a duplicate key error, causing the version to be revealed in the error output. This is particularly effective against web applications connected to MySQL backends where error details are exposed. The target environment is typically a vulnerable web form or parameter (e.g., login or search field) that concatenates user input directly into a SQL query. Success allows extraction of database metadata, which can lead to further enumeration of tables, users, or data exfiltration.

## Requirements

1. Access to a web application vulnerable to SQL injection with a MySQL backend (version 4.1+).
2. Knowledge of the injection point (e.g., a URL parameter or form field).
3. Tools for intercepting and modifying HTTP requests, such as a browser or proxy (though not required for basic manual injection).
4. Basic understanding of SQL syntax and MySQL error handling.

## Defense

- Use prepared statements and parameterized queries to separate SQL code from user input.
- Implement input validation and sanitization to reject suspicious characters (e.g., quotes, unions).
- Configure MySQL to suppress detailed error messages (e.g., via sql_mode or custom error handlers in the application).
- Monitor application logs and database queries for anomalies like unexpected RAND() or GROUP BY usage.
- Apply web application firewalls (WAFs) to detect and block common SQL injection patterns.

## Objectives

1. Confirm MySQL version compatibility and extract the server version via error messages.
2. Demonstrate data leakage through database errors to enable further exploitation.
3. Bypass input validation to inject and execute arbitrary SQL subqueries.

## Instructions

### Step 1: Verify MySQL Server Version Compatibility

**Context**: Before attempting injection, query the database version to ensure it supports the error-based technique (MySQL 4.1+). This step assumes you have an injection point; if direct access is available, use it to confirm.

**Command** ([[commands/mysql-query-server-version]]):
```sql
SELECT VERSION();
```

> This command retrieves the MySQL server version. If the version is 4.1 or higher, proceed. In an injection scenario, adapt this into the payload for the vulnerable parameter.

### Step 2: Inject the Error-Based Payload to Extract Version

**Context**: Craft and inject the payload into the vulnerable parameter to trigger a duplicate entry error, leaking the @@VERSION value in the error message. This step explains the payload's mechanics: the subquery creates inconsistent grouping with RAND(), causing a duplicate key error that includes the concatenated version info.

**Code** ([[codes/MySQL-Error-Based-Duplicate-Entry-Payload-for-Version-Extraction]]):
```sql
(select 1 and row(1,1)>(select count(*),concat(CONCAT(@@VERSION),0x3a,floor(rand()*2))x from (select 1 union select 2)a group by x limit 1))
'+(select 1 and row(1,1)>(select count(*),concat(CONCAT(@@VERSION),0x3a,floor(rand()*2))x from (select 1 union select 2)a group by x limit 1))+'
```

> Inject this payload into the vulnerable input field (e.g., append to a URL parameter like ?id=1' [payload] --). The CONCAT function appends the version to a colon-separated value, and the GROUP BY with FLOOR(RAND()) forces the error. Observe the application's error response for the leaked version (e.g., 'Duplicate entry '5.7.XX:1' for key 'group_key''). If successful, the version is visible in the error details.
